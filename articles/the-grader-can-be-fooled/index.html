The Grader Can Be Fooled: Building an Evaluation That Survives Its Own Shortcut

A shortcut returned the right ratio on every task without fitting a single spectrum, and the repair that followed is a field guide to measuring agents honestly: reuse the open parts, attack the grader, and keep the traces.

Ovia Inc · Studio and Lab · 6 min read

A score can be correct and still prove nothing. In a laboratory exercise published this week, a short script read the tallest point of each peak in a spectrum, guessed the widths, divided one height by another, and produced exactly the ratio the grader expected, on every task, without fitting a single spectrum. A verifier that checked only the final ratio would have passed the shortcut. An evaluation earns trust only when the check examines the work, not just the answer.

On November 23, 2026, Hugging Face published a guide to building and maintaining agentic evaluations: reuse open tasks instead of starting from blank pages, test the test before testing any model, and open the machinery of measurement for inspection, correction and reuse. The guide arrives as agent scores drive deployment decisions on thin evidence: 98.2 percent of model-benchmark scores are reported by only one party, with no second run to compare against.

The worked example stays deliberately small. A physics laboratory wants an agent to fit peaks in a Raman spectrum of graphene, calculate a defect ratio from two of those peaks, and save accurate results. The builders reused an open terminal task through the Harbor evaluation harness, ran the reference solution, then adapted the task into eight synthetic spectra with known parameters and varied noise: fitting spectra supports a claim about fitting spectra, and nothing grander.

Key points

  • The Hugging Face guide, published November 23, 2026, builds agentic evaluations by reusing open tasks, environments and verifiers, and validates hard.
  • A shortcut that skipped the required fitting returned the expected defect ratio on all eight adapted tasks; the verifier was rebuilt to check the fitted peaks themselves.
  • With the model held fixed, changing only the agent harness moved accuracy by up to 29.9 percentage points in a Terminal-Bench audit cited by the guide.
  • Scores need traces: on the adapted tasks, most failures came from an agent stopping early, a cause no headline score could show.

01 · The announcement

The guide organises evaluation history into three eras. Question-and-answer benchmarks checked a response against a key. Agentic benchmarks check what an agent changed inside an environment: files written and state left behind. A third era, now forming, scores what teams of agents produce together. Each step adds surrounding software that can move the score, which is why the guide dissects one evaluation into parts: the task, the pinned environment, the harness and its tools, the rollout, the trace, the verifier, and the claim the assembly supports.

Building follows eight steps: define the claim, find a task, run the task unchanged, adapt the task, check the evaluation, read the traces, report the score, and compare models. Reuse carries most of the weight: in the laboratory example, only the agent harness needed no new work, and the Hub already hosts the raw material in public, around 3,500 evaluation leaderboards and roughly 17,000 evaluation datasets, as reported in the guide.

02 · Why it matters

An agent score is a claim about a system, and the system includes everything around the model. The guide cites an audit of Terminal-Bench where researchers held the model fixed and changed only the agent harness: accuracy moved by up to 29.9 percentage points. Two products can publish honestly measured scores for the same model and describe materially different performance, because the harness and the environment sat inside the measurement. Comparing headline numbers without the harness pinned and named compares assemblies, not models.

The stakes compound in operations. Healthcare, finance and engineering teams increasingly choose agent systems on published evaluations. An untested grader, a contaminated task set or a harness nobody else can run offers confidence without evidence. The remedy is scrutiny by design: publish the parts reviewers need, and keep a correction record.

A verifier that checked only the ratio would have given the shortcut full marks on all eight tasks.

03 · The craft angle: grade the work, not the answer

Context engineering at Ovia since December 2022 treats the verifier as part of the product, and the laboratory story shows why. Before running more models, the builders attacked the evaluation three ways: the reference solution had to pass every task, an agent that did nothing had to fail, and a shortcut that skipped the required skill had to fail. The shortcut passed the first grader, so the grader changed: checks moved onto each fitted peak, within tolerances that pass faster valid methods and fail methods that skip the task.

Traces complete the discipline. On the original task, an open-weight model passed none of three attempts, and the score alone hid why. The traces showed the cause: most failures across the adapted set came from the agent declaring completion early, often after a missing package stopped the first script. Across eight tasks with three attempts each, eleven attempts passed; seven tasks passed at least once, while only one passed every time. For unattended processing, consistency is the metric that matters, and only the trace explains the gap.

We apply the same order of work in agent operations: pin the harness, version recorded beside every score, test the grader with a known-good run, a known-empty run and a known shortcut, and read traces before believing any aggregate.

04 · Caveats and fine print

Every figure in the guide deserves its qualifier. The harness swing, the single-party reporting share and the benchmark-flaw findings come from studies the guide cites, and the laboratory results rest on eight development tasks, too small to generalise from: a repeat run differed by one attempt. Three of six models compared passed every adapted task, so the set cannot rank the strongest systems at all. A cited review found flaws in task setup or reward design able to shift measured performance by up to one hundred percent, and public review later corrected twenty-eight of eighty-nine tasks in one terminal benchmark while leaving rankings stable.

Openness carries a tension the guide states plainly. Publishing tasks enables scrutiny, and exposes tasks to training data. Holding test items back limits contamination, yet private items still saturate once a benchmark is adopted. The proposed balance is strategic: open the infrastructure, grading methods, traces and correction history, and protect active test items behind controlled review.

05 · What to watch

Watch for evaluations that publish like instruments: versioned tasks, named harnesses, traces linked to scores, uncertainty beside every headline figure, and an honest correction history. Watch for the afterlife: a solved task becomes a regression check for the next harness, and a verifier seeds a harder successor. Measurements built in the open keep working after the leaderboard stops separating the field.

We read the guide as a standard worth adopting wherever a score informs a decision: reuse what the community has already validated, attack the grader before trusting the grade, and keep the evidence where a sceptical reader can reach it. The shortcut that earned full marks did the field a favour. Every evaluation deserves one, early, from a friendly hand.
