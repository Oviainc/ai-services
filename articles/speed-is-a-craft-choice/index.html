Speed Is a Craft Choice: Decoding Belongs in the Design Phase

The numbers on the table

One table in NVIDIA's October 30, 2026 technical post deserves more attention than the headline around it. Running Nemotron-3.5 Lightning on a DGX Spark in the 64GB configuration, through TensorRT Edge-LLM, NVIDIA reports mean generation speed on SpeedBench 1K rising from 73.3 tokens per second with DSpark speculative decoding off to 108.5 with DSpark on. On HumanEval prompts, the same switch moves generation from 73.4 to 126.9 tokens per second. Median time to first token barely changes — 201 milliseconds off, 203 on, for the 1K workload. Every figure is vendor-reported, measured by NVIDIA on NVIDIA hardware, under a specific test setup: batch size one, a single streaming request, a 128-token output limit, three draft tokens in the DSpark configuration.

How speculative decoding buys speed

The mechanism is a wager with a referee. A fast, cheap drafting process proposes several tokens ahead; the full model verifies the proposals in one pass, accepting the stretches that hold and correcting the first point of divergence. When drafts are good, several tokens land for roughly the cost of one full step. When drafts are poor, verification still guarantees the output matches what the full model would have produced — the speed is opportunistic, the correctness is not. Draft length, draft source and acceptance behaviour become tuning surfaces, closer to engine building than to prompting.

Why the first token barely moves

The flat time-to-first-token line is the honest detail in the table, and the instructive one. Speculative decoding accelerates the long middle of a generation; the wait for the first token is governed by prompt processing, which drafting does not touch. Two different latencies, two different levers. Systems that feel fast attend to both: prompt-side work — context size, caching, prefill efficiency — for the opening moment, and decoding strategy for everything after. Conflating the two produces optimisation programmes that improve the number nobody was waiting on.

The design-phase argument

Agent workloads multiply whatever the decoding layer decides. A single user request fans out into planning, tool calls, verification and revision — dozens of generations, each paying the per-token rate. A gain near fifty percent, of the size NVIDIA reports on the 1K workload, compounds across every loop the agent runs, and lands directly in operating cost and in how responsive the system feels. That is why decoding strategy belongs in the design phase, beside quantisation, engine builds and context budgets — the cluster of decisions the discipline behind NVIDIA-Certified Professional: AI Operations treats as the craft itself, and the same cluster context engineering at Ovia weighs before an agent ever meets a user.

What to watch

Watch for independent reproductions on real agent workloads rather than benchmark prompts, for drafting strategies tuned per workload instead of per demo, and for serving stacks that expose decoding choices as first-class configuration. The deeper shift is cultural: generation speed stops being a property a model simply has, and becomes a property a team designs, measures and defends — a craft choice, made on purpose.

A second discipline follows from the flat first-token line: measure the two latencies separately, in production, per workload. Benchmark tables report medians on clean prompts; real estates serve long contexts, warm and cold caches, and users who judge the whole system by the pause before the first word appears. Teams that instrument both numbers can spend effort where the waiting actually happens — prefill and context handling for the opening moment, decoding strategy for the long generation that follows — instead of celebrating an average that hides both problems at once.
