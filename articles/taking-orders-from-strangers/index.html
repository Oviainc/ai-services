Taking Orders From Strangers: Verify the Tool Before the Agent Trusts It

A poisoned tool never needs to run malicious code when the agent already holds the permissions: OX Security counted the instructions, the missing owners and the unverifiable code behind the tools agents plug into.

Ovia Inc · Studio and Lab · 6 min read

Ovia Inc — Cybersecurity · Agent Supply Chain

Key points

  • OX Security, November 23, 2026, analysed 542,207 components across npm, PyPI, MCP servers and Agent Skills, collected July to October 2026.
  • Prompt injection and tool poisoning appeared in 22 percent of flagged MCP servers, ahead of install-time execution at 16 percent.
  • None of the 179 flagged Skills ran code at install, yet 44 percent instructed agents to send data out.
  • For 83 percent of flagged MCP servers, researchers could not independently verify that deployed code matched what publishers declared.
The agent already has the permissions it needs. Attackers just have to convince it to use them.

The oldest rule of the workshop floor also governs the newest software: never plug in a drive found in the car park. Nobody knows who left the drive or what the drive will do once connected. Agents break that rule as a matter of routine. An agent connects to a tool server, loads a skill file, pulls a package from a public registry, and then acts on what those components say, often with access to files, credentials and production systems already granted.

On November 23, 2026, OX Security published Plug and Pray, a study of that habit at registry scale. The research team analysed 542,207 open source components across npm, PyPI, MCP servers and Agent Skills, flagging suspicious components with the OX Radar early-warning system and then investigating the flags. Findings were collected between July and October 2026. The headline is not a new exploit. The headline is a change of medium: the payload can now be an instruction.

Among flagged MCP servers, prompt injection and tool poisoning appeared in 22 percent, ahead of install-time or import-time execution at 16 percent. Agent Skills sharpened the contrast. None of the 179 flagged Skills executed code at install, yet 44 percent contained instructions directing agents to send data out. No malicious program needs to run when the agent already holds the permissions and can be persuaded to use them.

01 · The announcement

Traditional supply chain attacks hide in code that runs: a package steals credentials during installation, downloads a payload, or opens a backdoor, and scanners hunt for malicious behaviour in the code itself. MCP servers and Agent Skills add a second surface beside the code. A server exposes tools together with the descriptions and instructions an agent reads before calling them, and a skill file shapes how an agent behaves across a whole task. When those instructions are hostile, the component never needs to execute anything. The agent performs the action, inside a session the operator authorised, with credentials the operator supplied.

The npm comparison shows how new the pattern is. In flagged npm packages, execution techniques were six times more common than prompt injection and tool poisoning, the reverse of the MCP pattern. Registries built for libraries carry a code problem; registries built for agents carry an instruction problem as well, and tooling tuned only for code walks past a poisoned description.

02 · Why it matters

Verification failed further behind than injection did. OX Radar identified a source owner for only 69.8 percent of MCP servers, against 92.8 percent of npm packages, so nearly one server in three arrived with no accountable publisher to assess. Of 834 flagged MCP servers, 67 percent ran on publisher-controlled infrastructure where the deployed code could not be independently confirmed, and another 16 percent served files that differed from what publishers declared. Together, 83 percent of flagged servers presented a code verification problem: the source a publisher shows does not establish the code an agent reaches.

Concentration compounds the gap. Two publisher accounts were responsible for 44 percent of flagged MCP servers, and one account published 2,364 servers in 17 days. Volume alone does not establish malicious intent, as the report states plainly. Concentration still changes the arithmetic: one compromised publisher account can stand behind thousands of tools already wired into other teams.

03 · The craft angle: three questions at the gate

The report closes with three questions, and the questions translate directly into intake craft. Who controls the tools our agents connect to, and can the publisher be identified at all? Can we verify the code those tools actually run, as deployed, rather than the code a listing describes? Will we know when that code changes on infrastructure nobody on the team controls? A tool that fails the first question never reaches the second: unnamed stays unconnected.

Context engineering at Ovia since December 2022 treats every connected component as part of the context an agent will obey, and context earns trust in stages. Before connection, we read tool descriptions and skill instructions as untrusted content, word by word, the way a contract gets read before signature. The publisher gets named in the project record, permissions get matched against the task, and anything asking an agent to move data outward gets refused until a human reviews the request. Field years taught the same discipline in another medium: at Staywired from 2014 to 2022 and at Beanfield Metroconnect from 2011 to 2013, a circuit stayed dark until the far end was identified and labelled. An agent connection deserves no less ceremony.

Change completes the discipline. Of researcher-confirmed malicious components, 82 percent were malicious in the first observed version, so watching updates alone cannot catch a component that arrived compromised. Trust gets reassessed at connection time and on a schedule, not only when a version number moves. A pinned inventory of connected servers and skills, each with a named owner and a review date, turns a vague worry into a short list a small team can work through.

04 · Caveats and fine print

Every figure in the study is OX Security-reported, from a vendor that sells application security, and the percentages describe flagged components rather than the whole ecosystem. Flagged means suspicious characteristics worth investigating, not proven malicious, and the report states the findings do not establish that every weakness was exploited. The Skills sample is small at 179 flagged items, in an ecosystem the authors call young. Percentages of a flagged set cannot be read as infection rates for every MCP server in production: the numbers map where scrutiny belongs, not a census of harm done.

One boundary matters for response planning. Nothing in the study indicts the MCP pattern itself: servers, skills and registries remain the practical way agents gain reach. The finding is narrower and more useful: trust signals built for libraries, download counts, star ratings and publisher pages, do not answer the questions agent connections raise.

05 · What to watch

Watch whether registries begin publishing the answers the report asks for: verified publisher identity as a listing requirement, deployed-code attestation for hosted servers, and change notices when a hosted tool alters behaviour between reviews. Watch whether harness builders surface tool descriptions for review at connection time, instead of burying the text an agent will treat as orders. And watch the follow-up research: independent replication on a broader sample will show how much of the flagged pattern survives second inspection.

The durable lesson is older than agents. A connection is a decision, and a decision needs a name, a record and a review date. Teams that inspect at the gate keep the convenience of connected agents without handing instructions to strangers. The craft is choosing, carefully and in writing, whose orders the agent is allowed to take.
