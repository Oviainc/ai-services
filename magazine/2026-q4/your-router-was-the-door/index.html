Your Router Was the Door: The GL.iNet Breach

A cloud management flaw let an unauthorized party install malware on GL.iNet routers and KVM devices. The vendor notice contains the whole remedy: one string to look for, one firmware to install, and a caveat worth reading at full size.

Renata Vidal · Ovia Inc · Studio and Lab · 8 min read

Key points

  • On November 20, 2026, GL.iNet identified a vulnerability in its cloud remote management services; an unauthorized party exploited it to install malicious software on some GL.iNet routers and KVM devices. The attack path is blocked and the cloud vulnerability is fixed.
  • The fix has an asymmetry every owner must understand: the cloud-side fix stops new infections through this path but removes nothing from devices already infected. The security firmware removes the malware, without a factory reset, and settings can be kept.
  • The check is one exact string: look for crond -i /tmp/.log in the details of a running process, on routers through LuCI or SSH, on KVM devices through the device terminal.
  • GL.iNet recommends the security firmware for the exact model even when the check finds nothing, states that an unlisted model is not necessarily unaffected, and warns that additional indicators have since been identified and the quick check may not detect every affected device.

1. The incident

The disclosure is dated November 20, 2026 and it is short enough to state whole. GL.iNet identified a vulnerability in its cloud remote management services. An unauthorized party exploited the vulnerability to access and install malicious software on some GL.iNet routers and KVM devices. The company fixed the cloud vulnerability and blocked the access used in the incident, so devices can no longer be newly infected through this attack path. Customer notifications are being prepared for accounts GL.iNet identifies as affected, and the investigation is ongoing, including the question of whether computers connected to affected KVM devices were impacted. The notice will be updated as the scope firms up.

Two properties of this incident deserve emphasis before the instructions, because they decide how an owner should react. The first is the target: not a firmware bug in one model, but the cloud service that manages the fleet. A vulnerability there is a vulnerability in every enrolled device at once, which is why the affected set is described as some routers and some KVM devices across the range rather than a single product line. The second is the asymmetry in the fix. Blocking the attack path protects the uninfected. It does nothing for a device where the malware is already installed and running. For those devices, remediation is a separate act, performed by the owner, with the security firmware. Everything below is that act, in the order GL.iNet prescribes it.

2. The check

For both routers and KVM devices, the indicator is one exact piece of text: crond -i /tmp/.log, appearing within the details of a running process. The process entry may contain other information; the string is the match. On a router there are two routes. Through the web admin panel: go to System, then Advanced Settings, sign in to LuCI, open Status, then Processes, and search the page (Ctrl+F, or Command+F on macOS) for tmp/.log, checking whether a matching process shows the full indicator. Through SSH: sign in to the router and run ps | grep tmp, then look for crond -i /tmp/.log in the output. A line showing only the grep command itself is not a match; that is the search looking for itself, and the notice says so explicitly because it is the false positive every owner will meet first.

On a KVM device, open the web interface, go to Toolbox, then Terminal, then Access, and run the command in the KVM's own terminal, not on the connected computer: ps -a | grep tmp on the RMQ1, and ps -aux | grep tmp on all other KVM models, looking for the same string. Three outcomes follow. If the indicator is found, treat the device as infected and go to section 3. If the check completes without finding it and there is no other reason to suspect infection, no factory reset or other cleanup is needed, and the security update is still recommended. If the check cannot be completed, or the result is unclear, GL.iNet's instruction is to contact support at support@gl-inet.com rather than guess.

3. The remediation

Install the latest stable security firmware for the exact model, as soon as possible, whether or not the check found the indicator. The security firmware removes the malware identified in this incident without requiring a factory reset, and existing settings can be kept during the update. Do not install firmware built for another model. The version floors in the notice: routers GL-MG1300, GL-MT3000 and GL-MT6000 at 4.11.1 or later; GL-E5800 at 4.10.3; GL-BE3600 and GL-BE9300 at 4.10.2; GL-BE14000 at 4.9.3; GL-BE6500, GL-MT3600BE and GL-MT5000 at 4.9.1; GL-BE10000 at 4.8.7; GL-AX1800, GL-AXT1800, GL-SFT1200, GL-X3000 and GL-XE3000 at 4.8.4; GL-MT2500, GL-MT2500A and GL-X2000 at 4.7.14. KVM devices: RM1, RM1V2, RM10, RM10RC, RM1PE and RM4PE at 1.10.3 or later; RMQ1 at 1.8.7. Anyone running a security beta should move to the latest stable. If a model is not listed, the notice is blunt that this does not mean it is unaffected: check the GL.iNet Download Center or write to support. If the upgrade fails, or the indicator is still present after the upgrade, contact support for recovery guidance.

One extension matters for KVM owners specifically. A KVM device is a keyboard, video and mouse channel into a computer, which is to say a trusted path into whatever it is attached to. If a KVM is infected, GL.iNet directs owners to check the connected computer as a precaution: unfamiliar programs, browser extensions or user accounts; unexpected startup items or scheduled tasks; unusual settings changes or network activity; and a full scan with up-to-date security software. The router's malware lives on the router. The KVM's risk lives one hop further in, and the sweep has to follow it there.

4. The limits of a clean check

The notice contains its own caveat section, and an honest piece enlarges rather than buries it. As the investigation continues, additional indicators of compromise have been identified, and the official quick checks may not detect every affected device. GL.iNet points to an independently developed community check tool for owners who want a more comprehensive pass, and surrounds the pointer with an unusually complete disclaimer: the tool is not developed, verified, maintained, endorsed or supported by GL.iNet, it may run with administrative privileges and includes optional remediation and evidence-collection functions to be evaluated carefully, and the absence of findings does not guarantee a device has never been compromised. Of the two checking approaches together, the notice concludes that neither can guarantee a device is free of compromise.

The firmware is the only step in the notice that removes the identified malware rather than looking for it.

Hold that beside the remediation instruction and the correct posture assembles itself. The process check is necessary and fast, and it catches the known malware in the known form. It is not a certificate. The firmware, by contrast, is for everyone: owners with the indicator, owners without it, owners who could not complete the check, because the firmware is the only step in the notice that removes the identified malware rather than looking for it. And the affected-customer emails, when they arrive at the address on the cloud account, are information, not a starting gun. The notice says plainly that nobody needs to wait for one to check a device or install the update.

5. The lesson: remote management is the key under the mat

GL.iNet makes good devices, and its travel routers and KVM units sit in an enormous number of homes, site cabins, classrooms, clinics and small offices precisely because they are manageable: reachable, updatable and administrable from a cloud console, by an owner who is somewhere else. That property is the product. This incident is its price, stated generally enough to apply far beyond one vendor: every remotely managed edge device is a door into the network it serves, and the remote management service is a key cut for every door in the fleet at once. Compromise the key cabinet and the locks on individual doors stop mattering. The devices behind those doors are rarely the hardened centre of anyone's estate. They are the shelf router, the KVM in the rack, the unit installed by a contractor and enrolled in a cloud account nobody has opened since.

The operating discipline that follows is unglamorous and entirely doable. Keep an inventory of remotely managed edge devices, vendor by vendor, with the cloud accounts that govern them named and owned. Turn cloud management off where the convenience is not actually used; a door nobody opens does not need a key in circulation. Treat firmware currency as a standing practice rather than an incident response, so that a security release is a routine Tuesday and not an emergency. And when a vendor discloses, run the fleet check the same week, every device, indicator or no indicator, because the vendor's list of affected models is a floor, not a ceiling, as this notice itself warns. For estates without the hands to do that across dozens of sites, a rapid device-fleet check and remediation, run as a service against the vendor's own published indicators and firmware, is the shape of the help. The router was the door. The work is knowing how many doors there are.
